# Coordination 生命周期 v0.1

> 覆盖三类生命周期：**版本**（release）、**语言特性**（feature）、**平台与项目**（platform / project）。
> 原则：破坏性变更只发生在预先声明的窗口；弃用必须可执行；兼容承诺写进章程，例外公开。

## 1. 版本模型：工具链 semver 与语言 edition 分离

| 对象 | 版本方式 | 说明 |
|---|---|---|
| 编译器/工具链 `coord` | SemVer 2.0.0 | major 破坏 CLI/缓存格式/`.cif` 格式；minor 加功能；patch 修 bug |
| 语言 | edition（约三年一个） | 语法/语义的破坏性变更只在 edition 边界发生，跨 edition 可互操作 |
| 标准库 | 跟随工具链 semver | 与语言 edition 解耦；弃用走 §4 |
| 包 | 各自 semver | 包管理器按 semver 解析依赖 |

edition 不是 semver major：同一项目内不同包可以用不同 edition，编译器同时支持全部历史 edition（参考 Rust 2015/2018/2021/2024 的做法）。每个 edition 对应一份"迁移指南 + `coord fix` 自动改写规则"。

## 2. 发布通道与节奏

| 通道 | 频率 | 稳定性 | 用途 |
|---|---|---|---|
| nightly | 每日 | 无承诺 | 新特性验证（feature gate） |
| beta | 每月 | 基本稳定 | 提前发现回归 |
| stable | 4 周（0.x）/ 6 周（1.0 后） | 承诺兼容 | 生产使用 |

- 0.x 阶段：每 4 周一个 minor，允许破坏（但仍需公告 + 迁移说明）。
- 1.0 后：6 周列车，只维护最新 stable 与上一个 minor 的安全修复；更老的版本由社区维护（Tier 3 待遇）。
- 紧急安全补丁：随时发 patch，不占用列车窗口。

## 3. 1.0 的进入门槛

1. 语言规范 1.0（条款编号稳定）+ 一致性测试覆盖每条条款；
2. 至少两个 Tier 1 平台全绿（Windows x64 + Linux x64），macOS 紧随；
3. `coord fix` 能在示例项目上完成 0.x → 1.0 迁移；
4. 标准库核心稳定（容器、字符串、I/O、错误、并发原语）；
5. 《兼容性章程》发布（见 §5）；
6. 至少 10 个真实示例项目与 3–5 个设计伙伴验证。

未达标不发 1.0；宁可延长 0.x。

## 4. 特性生命周期

```text
提案(RFC) → nightly(gate) → beta → stable → deprecated → removed
```

| 阶段 | 要求 | 退出条件 |
|---|---|---|
| nightly | feature gate 名称稳定，文档标注"实验性" | 至少一个发布周期无重大问题 |
| beta | 默认开启，可回退 | 一致性测试 + 规范条目 |
| stable | 写入规范，错误码稳定 | — |
| deprecated | `@deprecated(since, note, replace_with)`，编译告警 | 至少 2 个 minor 或 12 个月（取较长者） |
| removed | 只在 edition 边界或 semver major 移除 | 迁移工具覆盖 |

**弃用必须是可执行的**：告警信息给出替代写法；`coord fix --edition` 能自动改写；文档同步更新。禁止"静默移除"或"先移除后公告"。

## 5. 兼容性章程（1.0 发布）

承诺：

1. **源码兼容**：stable 代码在新版本上继续编译，语义不变（除 §5.2 例外）。
2. **edition 兼容**：跨 edition 的包可互相调用；同一构建内混用 edition 合法。
3. **C ABI**：`extern "C"` + `repr(C)` 的类型布局与调用约定稳定。
4. **CLI 兼容**：`coord` 子命令与参数在 major 内不破坏；新参数默认关闭。
5. **`.cif` 格式**：major 内向后兼容；新格式可被旧编译器识别或明确报错。

不承诺：

- 原生 ABI（结构体布局、name mangling、vtable 布局）跨编译器版本稳定；
- 编译器内部 API、缓存格式、诊断文案逐字不变；
- 未定义行为、编译器 bug 的表现。

例外（必须公告 + 影响范围 + 迁移建议）：安全漏洞、编译器正确性缺陷、平台 API 变更、依赖的 LLVM/系统库不兼容。

## 6. 平台生命周期

| 级别 | 进入条件 | 维持条件 | 退出流程 |
|---|---|---|---|
| Tier 1 | 有维护者 + CI 机器 | 每次提交全量测试 | 连续两个版本无法维持 → 公告降级 |
| Tier 2 | 可交叉编译 + 每周测试 | 构建可复现 | 一个版本未通过 → 降 Tier 3 |
| Tier 3 | 社区维护 | 无 SLA | 可随时移除，保留源码补丁说明 |

平台降级/移除至少提前 **一个 minor** 公告，并在发布说明中列出最后可用版本。`*-none-*`（freestanding）与 `wasm32-*` 作为独立目标族单独维护，不占用 Tier 1 名额。

## 7. 项目自身的生命周期

| 阶段 | 判定 | 关键动作 |
|---|---|---|
| 启动（当前） | 规范草案 + 宿主库 | 定语言规则、搭 CMake/CTest、跑通示例 |
| MVP | 端到端可编译运行 | 固定 span/诊断、TargetSpec、`.cif` 三个契约 |
| 自举 | 标准库与前端用 coordination 写 | stage2/stage3 输出一致；三平台 CI |
| 生态 | 外部包与真实用户 | 注册表、签名、兼容性章程、1.0 |
| 维护 | 1.0 之后 | 6 周列车 + edition 三年周期 + 安全响应 |
| 归档 | 维护者不足或方向终止 | 冻结仓库、保留构建脚本与最后版本说明 |

**bus factor 防护**：每个 Tier 1 平台至少 2 名维护者；核心组任何角色有备份；关键流程（发布、安全响应）有书面 runbook。

## 8. 治理生命周期

- 核心组 5 人，任期 12 个月，可连任；每年公开回顾一次决策记录。
- 维护者晋升：持续贡献 6 个月 + 2 名现有维护者提名 + 核心组简单多数。
- 资金：早期 GitHub Sponsors / Open Collective；出现 2 家以上稳定赞助方后再考虑基金会，避免单一赞助方俘获。
- 决策记录公开；被否提案保留在 RFC 仓库，供后来者查阅。

## 9. 里程碑与检查点

| 检查点 | 频率 | 输出 |
|---|---|---|
| 每周工程同步 | 每周 | 阻塞项、CI 健康度、性能回归 |
| 版本回顾 | 每个 minor | 延期原因、破坏性变更清单、迁移完成率 |
| 季度复盘 | 每季度 | 采用数据、issue 首响、RFC 周期、路线图调整 |
| 年度治理回顾 | 每年 | 核心组改选、章程修订 |

## 10. 主要风险

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 兼容性承诺过早 | 1.0 前频繁改语法 | 延长 0.x，用 edition 承载破坏 |
| 平台矩阵失控 | Tier 1 平台维护者不足 | 降级机制 + 明确 SLA |
| 弃用不执行 | 告警堆积、迁移工具缺失 | 弃用必须带 `coord fix` 规则，否则不批 |
| 治理僵化 | RFC 周期持续 > 60 天 | 引入裁决时限与授权 delegate |
| 资金断档 | 无全职维护者 | 商业支持/培训收入，控制范围 |
