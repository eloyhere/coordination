# Coordination 项目流程 v0.1

> 目标：让"语言语义 → 编译器实现 → 工具链 → 发布"这条链路可预测、可审计、可回滚。
> 配套文档：`docs/language-spec.md`、`docs/architecture.md`、`docs/lifecycle.md`。

## 1. 基本原则

1. **设计先行**：语义先写进规范，再写实现；规范与实现不一致时以规范为准，或先改规范。
2. **小步合并**：一个 PR 只做一件事；语言级变更必须能独立回滚（feature gate）。
3. **文档进 CI**：规范里的示例、教程里的代码都要能编译运行，防止文档腐烂。
4. **决策留痕**：架构决策写 ADR，语言决策写 RFC，被否方案也要记录理由。

## 2. 角色与决策权

| 角色 | 职责 | 决策权 |
|---|---|---|
| 语言负责人 | 语法/语义/类型系统 | 语言变更最终裁决，须公开书面理由 |
| 编译器负责人 | 前端/IR/后端/诊断 | 实现路线与性能预算 |
| 工具链负责人 | driver、包管理、fmt/lint/LSP | 工具链接口与兼容 |
| 发布负责人 | 版本窗口、分支、发布检查单 | 是否发版、是否延期 |
| 社区/生态 | RFC 运营、文档、设计伙伴 | 流程与社区规范 |

核心组 5 人，语言设计变更需 **2/3 同意**；平票或僵局由语言负责人裁决并公开理由。设计评审与代码评审分离：RFC 阶段不评审具体实现，实现阶段不重新辩论语义（除非发现规范缺陷，走修订流程）。

## 3. 变更分级

| 级别 | 例子 | 流程 |
|---|---|---|
| L0 编辑性 | typo、注释、文档措辞 | 直接 PR，1 人批准 |
| L1 实现/重构 | 修 bug、加测试、内部重构 | PR + 1 名 reviewer + CI 全绿 |
| L2 架构/工具链 | 新模块、缓存策略、CI 矩阵、依赖升级 | PR + 设计说明 + 2 名 reviewer + ADR |
| L3 语言语义/语法 | 新关键字、覆盖规则、import 语义 | RFC + 实现（feature gate）+ 一致性测试 + 规范修订 |

**任何级别都不允许直接 push `main`**；`main` 受保护，必须 PR + CI 通过。

## 4. RFC 流程（L3）

1. **提案**：在 `coordination-rfcs` 仓库提 PR，模板固定包含：动机、语法/语义、兼容性影响、迁移方案、替代方案、未决问题。
2. **评论期**：7 天公开评论；提案人指定 champion 推进。
3. **最终评论期（FCP）**：10 天；无未解决反对则进入裁决。
4. **裁决**：语言负责人 2/3 核心组同意后接受/拒绝/延期；理由写入 RFC。
5. **实现**：接受后进 nightly，用 feature gate 隔离；至少一个完整发布周期验证。
6. **稳定**：一致性测试 + 规范条目 + 迁移说明齐备后转 stable。

紧急安全/正确性修复可走快速通道（24 小时内裁决），但事后必须补 RFC 记录。

## 5. 日常开发流程

```text
issue（模板：bug/feature/rfc-track）
  → 分支 feat/<slug> 或 fix/<slug>
  → PR（描述：动机、方案、测试、兼容性）
  → CI（格式、构建、单测、一致性、clippy 级 lint）
  → 1–2 名 reviewer 批准
  → squash merge 到 main
  → nightly 自动构建
```

约定：

- 提交信息用 `area: summary`（如 `parser: 支持 @cfg 声明`），body 写"为什么"而不是"改了什么"。
- PR 必须自带测试；修 bug 必须先有失败用例。
-  breaking change 必须在 PR 标题标注 `[breaking]` 并链接 RFC/edition。
- 依赖升级单独 PR，附变更日志摘要与许可证检查。

## 6. 测试策略

| 层级 | 内容 | 门槛 |
|---|---|---|
| 单元测试 | 宿主库（`structure/`、`syntax/`）与编译器各 pass | 全绿；新增代码覆盖率不低于所在模块均值 |
| 一致性测试 | `conformance/` 下按规范条款编号的用例，正例 + 反例（应报错且错误码正确） | 每条规范条款至少一个用例 |
| 差分测试 | 同一程序在 LLVM 后端不同优化级别/不同平台输出一致 | nightly |
| 模糊测试 | lexer/parser、增量缓存、comptime 解释器 | 持续运行，崩溃即 issue |
| 性能基准 | 编译时间（hello、增量、10k 行）、运行时间、二进制体积 | 回归超过 5% 阻塞合并 |
| 跨平台矩阵 | Tier 1 全量、Tier 2 每周 | PR 阻塞 Tier 1 |

宿主库当前用 CTest 驱动（`tests/test_*.cpp`），新增测试文件自动纳入；语言侧一致性测试单独建 `conformance/`，按 `spec/<章节>/<条款号>.cn` 组织。

## 7. CI 与门禁

- PR 门禁：格式检查 → 构建（Debug/Release）→ 单测 → 一致性测试 → 文档示例编译。
- nightly：Tier 1 三平台 + sanitizer（ASan/UBSan）+ 模糊测试 + 性能基准。
- 发布门禁：全矩阵 + 迁移工具 `coordination fix` 在示例项目上跑通 + 发布检查单。
- 缓存：CI 复用 `coordination` 的查询缓存；缓存键含编译器版本与 TargetSpec，命中失败必须回退全量而不是报错。

## 8. 文档流程

- 四类文档：**规范**（权威语义）、**参考**（API/CLI）、**教程**（任务导向）、**示例**（可运行项目）。
- 每个规范条款有稳定编号（如 `§3.3-2`），一致性测试与错误码引用该编号。
- 文档随版本发布，保留历史版本；中英双语，中文为母本、英文同步。
- 示例代码进 CI；教程按任务组织（解析参数、读写文件、调用 C 库、发布二进制），不按语法章节排列。

## 9. 发布流程

1. 发布负责人在 `main` 上切 `release/x.y` 分支。
2. 跑发布检查单：全矩阵 CI、一致性测试、`coordination fix` 迁移验证、变更日志、文档版本。
3. 打 tag（`vX.Y.Z`），构建三平台产物，签名并生成校验和。
4. 发布公告：亮点、破坏性变更、弃用项、迁移命令。
5. 回滚预案：保留上一版本产物与安装包；严重缺陷走 patch 版本，不撤回已发布版本（必要时 yank 包而非删包）。

版本号规则与支持窗口见 `docs/lifecycle.md`。

## 10. 安全与供应链

- 漏洞响应：私有渠道报告 → 48 小时内确认 → 修复与公告同步 → CVE（如适用）。
- 发布物签名 + SHA-256 校验和；包注册表启用 OIDC 短期令牌与 provenance。
- 依赖审计：第三方依赖固定版本、记录许可证、每季度复查；LLVM 大版本升级单独演练。

## 11. 度量

| 指标 | 用途 | 反指标 |
|---|---|---|
| 下载量 / 活跃项目数 | 采用度 | stars、fork 数 |
| CI 通过率、平均修复时间 | 工程健康 | 提交数 |
| issue 首响时间、RFC 周期 | 社区健康 | 会议次数 |
| hello 编译时间、增量时间、二进制体积 | 产品体验 | 功能数量 |
